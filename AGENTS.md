# Repository guidance

These instructions apply to every change in this repository.

## Project boundary

`hoot-polars` reads supported `.hoot` inputs directly and exposes checked physical
records, typed updates, Polars DataFrames, and Parquet output. Keep production
code deterministic, local, and independent of external executables or network
services.

Do not create a Git commit, tag, release, or remote without an explicit
maintainer request. The maintainer must review the complete uncommitted tree
before history is created.

## Development provenance

All implementation code currently in this repository was generated by AI
under maintainer direction. Preserve that disclosure in public documentation.
Do not claim that generated implementation code was personally authored by a
human. Maintainers remain responsible for reviewing, testing, selecting, and
accepting changes.

New contributions must identify their provenance and confirm that the
contributor has the right to offer them under `MIT OR Apache-2.0`.

## Legal and provenance guardrails

- Do not add proprietary binaries, firmware, libraries, installers, generated
  vendor assets, or third-party source without explicit redistribution rights.
- Do not decompile, disassemble, decrypt, bypass access controls, or extract
  implementation content from proprietary software.
- Implement interoperability behavior in original code. Keep only functional
  facts needed for compatibility: identifiers, byte layouts, bit positions,
  numeric transforms, units, and enum values.
- Do not copy or closely paraphrase vendor-authored descriptions, examples, or
  documentation prose into code, metadata, tests, or documentation.
- Use product and company names only as necessary to describe compatibility.
  Do not use vendor logos or imply affiliation, sponsorship, or endorsement.
- Cite applicable public specifications and licenses when adding externally
  sourced material. Record the exact source and license in
  `THIRD_PARTY_NOTICES.md` when material is included.
- Treat robot logs and converted telemetry as confidential unless their owner
  explicitly authorizes publication. Never commit identifying paths, hashes,
  device serials, team data, or competition telemetry.

## Test data

Normal tests must be hermetic and use synthetic data committed under
`tests/fixtures/` or generated in test code.

A maintainer-authorized `.hoot` input and corresponding `.wpilog` output may be
used for local differential testing. Keep both files outside the repository or
ignored, pass paths through environment variables, and do not record their
paths, hashes, contents, or results in committed files. Any temporary comparison
script must be generated outside the repository and removed after use.

The ignored external-input test uses `HOOT_TEST_INPUT`. It must skip cleanly or
remain ignored when no authorized input is configured.

## Engineering requirements

- Keep parsing bounds-checked and panic-free for malformed input.
- Preserve strict and lenient tail behavior and resource limits.
- Report unsupported records explicitly rather than guessing semantics.
- Keep catalog metadata factual and free of descriptive summaries.
- Use deterministic simple column names and reject collisions.
- Add focused tests for every parsing, catalog, or naming change.
- Do not weaken tests merely to accept a new result.

Before handing off a change, run:

```text
cargo fmt --all -- --check
cargo test --locked
cargo clippy --all-targets --locked -- -D warnings
cargo package --list --allow-dirty --locked
```

Also scan the complete package list and source tree for private data,
proprietary assets, copied prose, credentials, and unexpected executable files.
